F5 ML-KEM Lab on AWS

Spin up a BIG-IP instance via AWS Marketplace, configure two VIPs side by side — one with ML-KEM enabled and one without — and verify the difference with openssl s_client. The goal is a working before/after you can run commands against yourself.

Version requirement: ML-KEM on F5 BIG-IP requires TMOS 17.5.1 or later. Earlier versions do not support the SecP256r1ML-KEM-768 cipher group. Confirm the AMI version before launching.

What This Lab Sets Up

A single BIG-IP VE instance in AWS with two virtual servers on the same public IP, on different ports:

Port 8443 — No ML-KEM

Standard TLS 1.3 with classical ECDH key exchange. This is the baseline — what most F5 deployments look like today without any PQC configuration.

Port 443 — With ML-KEM

TLS 1.3 with SecP256r1ML-KEM-768 cipher group enabled. A compatible client will negotiate X25519MLKEM768 as the key exchange group.

Both VIPs point to the same backend pool. The only difference is the Client SSL profile attached to each. You can run identical openssl s_client commands against both ports and observe the negotiated key exchange group change.

Launch F5 BIG-IP via AWS Marketplace

1
Find the listing
In the AWS Console, go to AWS Marketplace → Discover products. Search for F5 BIG-IP Good PAYG. Select "F5 BIG-IP Virtual Edition — GOOD (PAYG, 25 Mbps)". GOOD includes full LTM SSL offloading and cipher group support — everything this lab needs. No separate license file required.
2
Check the version
On the product page, click Continue to Subscribe, then Continue to Configuration. Under Software Version, select 17.5.1 or later. If only 17.1.x or 16.x are listed, check the BYOL listing which may carry a newer AMI.
3
Choose region and launch method
Select your region, then click Continue to Launch. Under Choose Action select Launch through EC2 — this gives you full control over instance type, networking, and security groups.
4
Instance type
Select m5.xlarge (4 vCPU, 16 GB RAM). This is sufficient for BIG-IP VE GOOD 25 Mbps in a lab. Smaller types may fail to boot or perform poorly under the SSL workload.
5
Network settings
Place the instance in a public subnet with auto-assign public IP enabled. For this single-NIC lab, one interface is enough — management and data plane share the same interface.
6
Security group
Create a new security group with the following inbound rules (source: your IP only): 
TCP 22    — SSH (initial access)
TCP 443   — VIP with ML-KEM
TCP 8443  — BIG-IP management UI + VIP without ML-KEM
ICMP      — ping (optional but useful)
7
Key pair and launch
Select your existing EC2 key pair. Click Launch Instance. The instance takes 3–5 minutes to pass both status checks and finish BIG-IP's internal initialisation.

Initial Configuration

Once the instance is running, retrieve its public IP from the EC2 console.

1
Set the admin password via SSH
BIG-IP PAYG instances use the EC2 instance ID as the initial admin password. SSH in and change it immediately: 
ssh -i F5.pem admin@<PUBLIC-IP>

# At the BIG-IP tmsh prompt:
modify auth user admin password <NEW-PASSWORD>
save sys config
Permissions error? If SSH complains the key is too open (permissions 0555), restrict it before connecting: 
# Linux / WSL (Ubuntu)
chmod 400 F5.pem

# Windows PowerShell (native SSH)
icacls F5.pem /inheritance:r /grant:r "$($env:USERNAME):(R)"
2
Access the management UI
Open https://<PUBLIC-IP>:8443 in your browser. Accept the self-signed cert warning. Log in as admin with the password you just set. The Setup Wizard will appear — you can skip it for this lab.
3
Confirm TMOS version
In the TMUI top-right corner the version is shown. Alternatively via SSH: 
show sys version | grep Version
Confirm it shows 17.5.1 or later before continuing.
4
Create a self-signed certificate
Both VIPs need a certificate. For this lab a self-signed cert is fine. Paste these commands into the tmsh prompt: 
create sys crypto key lab-key { key-size 2048 key-type rsa-private }
create sys crypto cert lab-cert { common-name lab.example.com key lab-key lifetime 3650 }
save sys config
5
Create a backend pool
Both VIPs need a pool. For this lab the backend doesn't need to be reachable — the TLS handshake (where ML-KEM is negotiated) completes before F5 attempts the backend connection. Use 192.0.2.1, an RFC 5737 reserved address that F5 accepts but that routes nowhere: 
create ltm pool lab-pool { members add { 192.0.2.1:443 { address 192.0.2.1 } } }
No monitor is set intentionally — without one F5 marks the member unchecked and still forwards, so the VIP stays green.

VIP without ML-KEM (Port 8443 — Baseline)

This is a standard TLS 1.3 virtual server with classical key exchange. It represents the current default state of most F5 deployments.

1
Create the Client SSL profile — no ML-KEM
create ltm profile client-ssl lab-ssl-classical { defaults-from clientssl cert lab-cert.crt key lab-key.key ciphers "TLS13-AES128-GCM-SHA256:TLS13-AES256-GCM-SHA384:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384" }
This profile uses classical ECDH groups (P-256, X25519) — no ML-KEM cipher group is attached. A client offering X25519MLKEM768 will fall back to classical negotiation.
2
Create the virtual server on port 8443
create ltm virtual lab-vip-classical { destination 0.0.0.0:8443 ip-protocol tcp pool lab-pool profiles add { lab-ssl-classical { context clientside } tcp { } } source-address-translation { type automap } vlans-enabled }

VIP with ML-KEM (Port 443)

This virtual server uses a Client SSL profile with the SecP256r1ML-KEM-768 cipher group. TLS 1.2 must be disabled — ML-KEM only works in TLS 1.3 via the key_share extension.

1
Create the ML-KEM cipher group
BIG-IP 17.5.1 introduces SecP256r1ML-KEM-768 as a named cipher. Create a cipher rule and group that includes it alongside classical fallbacks: 
create ltm cipher rule ml-kem-rule { cipher "TLS13-AES128-GCM-SHA256:TLS13-AES256-GCM-SHA384" key-exchange "SecP256r1ML-KEM-768:X25519:P-256" signature "RSA-PSS-SHA256:ECDSA-SHA256" }
create ltm cipher group ml-kem-group { allow { ml-kem-rule } ordering default }
2
Create the Client SSL profile — with ML-KEM
Attach the cipher group and force TLS 1.3 only. Setting no-tlsv1-2 ensures only TLS 1.3 connections are accepted, which is required for ML-KEM to negotiate: 
create ltm profile client-ssl lab-ssl-mlkem { defaults-from clientssl cert lab-cert.crt key lab-key.key cipher-group ml-kem-group ciphers none }
3
Create the virtual server on port 443
create ltm virtual lab-vip-mlkem { destination 0.0.0.0:443 ip-protocol tcp pool lab-pool profiles add { lab-ssl-mlkem { context clientside } tcp { } } source-address-translation { type automap } vlans-enabled }
4
Save configuration
save sys config

Testing the Difference

You need OpenSSL 3.5+ on your test machine. See OpenSSL Setup if you haven't built it yet. Run both commands against the same public IP.

Test port 8443 — classical (no ML-KEM)

openssl s_client -connect <PUBLIC-IP>:8443 -groups X25519MLKEM768:X25519:P-256 2>&1 | grep -E "Protocol|group|Cipher"

Expected output — the client offered ML-KEM but the server didn't support it, so they fell back to classical X25519:

Protocol  : TLSv1.3
Negotiated TLS1.3 group: X25519
Cipher    : TLS_AES_256_GCM_SHA384

Test port 443 — with ML-KEM

openssl s_client -connect <PUBLIC-IP>:443 -groups X25519MLKEM768:X25519:P-256 2>&1 | grep -E "Protocol|group|Cipher"

Expected output — both sides support ML-KEM, so it is negotiated:

Protocol  : TLSv1.3
Negotiated TLS1.3 group: X25519MLKEM768
Cipher    : TLS_AES_256_GCM_SHA384
The one line that tells the whole story: Negotiated TLS1.3 group: X25519MLKEM768 on port 443 vs Negotiated TLS1.3 group: X25519 on port 8443. Same client, same server IP, same cipher — the only difference is whether the Client SSL profile includes the ML-KEM cipher group. That is the entire configuration delta between a classically vulnerable TLS session and a post-quantum protected one.

Teardown

The instance costs money while running. When you're done testing, terminate it from the EC2 console. There is no persistent storage to worry about — all BIG-IP configuration lives on the instance root volume which is deleted on termination. 

# Confirm both VIPs are tested, then terminate via AWS Console:
# EC2 → Instances → select instance → Instance State → Terminate
